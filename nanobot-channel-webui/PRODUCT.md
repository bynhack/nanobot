# Product

## Register

product

## Product Positioning

`nanobot-channel-webui` 现在不是一个单纯的 nanobot 浏览器聊天入口，而是一个面向案件研判的 WebUI 工作台插件。

它的核心工作流是「案件池 + 当前案件 + 上图分析 + 对话辅助」：用户围绕一个案件选择主体、创建关系图、执行分析上图、在节点上钻取上下游、查看交易明细，并把每一步图结构和布局状态保存成可追踪的过程文件。聊天仍然重要，但它服务于案件分析、文件工作区、工具结果解释和操作辅助，不再是产品的唯一主线。

产品入口默认进入上图工作台，不再提供与上图并列的纯对话入口。对话运行时仍然保留，但它作为图谱研判右侧辅助区、全屏研判对话、工具结果查看和工作空间文件入口存在；通用设置入口放在上图工作台内。

这个产品的主界面应该像一个经侦分析桌面：中间关系图是核心研判画布，左侧承载案件和主体选择，右侧承载图详情、交易明细、对话和过程上下文。任何新增能力都应该优先回答一个问题：它是否帮助用户更稳定地完成一层一层的线索分析？

## Users

`nanobot-channel-webui` 面向需要在浏览器中完成案件研判、图谱分析和 AI 辅助操作的实际使用者与维护者。

核心用户包括：

- 经侦分析人员：按案件选择嫌疑人、账号和交易主体，通过上图分析、上下钻、交易明细和图步骤回放梳理资金线索。
- 案件研判负责人：需要查看当前图状态、过程步骤、排除项、钻取结果和关键关系，判断分析路径是否可靠。
- 高频办公用户：在对话中发起任务、查看工具结果、预览文件、下载生成内容，并把结果纳入案件工作流。
- 管理员：负责安装插件、配置 `channels.webui_plugin`、管理技能、检查运行状态、处理认证和会话数据。
- 插件维护者：需要在不修改上游 `nanobot-ai` 核心代码的前提下，迭代 WebUI、兼容 runtime 漂移，并保证本地构建发布流程稳定。

用户的使用环境偏向桌面浏览器和内部系统场景。产品重点不是营销展示，也不是通用聊天玩具，而是可靠呈现案件关系、保存研判过程、保护图谱状态，并让 AI 能在真实业务上下文里发挥辅助作用。

## Product Purpose

这个插件把 nanobot 的 gateway 能力包装成一个可独立安装、可随主工具环境启动的案件研判工作台。它保持上游 `nanobot-ai` 的安装和启动方式不变，通过 `nanobot.channels` entry point 提供浏览器入口、HTTP / WebSocket 后端、上传签名、会话索引、设置页、可选 PocketBase 账号体系，以及 case-graph 上图分析能力。

当前产品目的包括：

- 提供稳定的浏览器 WebUI，让用户可以继续通过 `nanobot gateway` 使用 nanobot。
- 提供案件上图分析工作台，把主体选择、关系图、钻取、交易明细、排除状态、群组状态和图配置组织在同一个业务界面里。
- 把关系图当前投影保存到 `case_graphs/{caseId}/{graphId}/graph.json`，并把每次关系分析操作保存到 `steps/*.json`，让图谱过程可恢复、可追踪、可对比。
- 在扩图、钻取、补关系和刷新过程中保护已有图布局位置，避免破坏用户已经形成的线索分析视图。
- 让聊天、工具调用、文件预览和工作区面板围绕案件研判服务，而不是脱离业务主线单独存在。

成功标准是：

- 用户可以用 `uv tool install nanobot-ai --with nanobot-channel-webui --force` 安装插件，并继续用 `nanobot gateway` 启动。
- 用户可以围绕案件创建图、分析上图、保存图状态、恢复图状态，并继续从某个节点扩展线索。
- 上图分析的每一步结构和布局都被保存；后续自动流程不会移动已有节点，除非用户明确执行了会改变位置的动作。
- 前端对齐 assistant-ui 的 runtime、Thread、Composer、Message、ThreadList 等最佳实践，同时把 case-graph 工作台作为当前业务主界面的一等能力。
- 聊天输入、中文输入、技能选择、附件上传、流式消息、表格、图片、工具调用、只读会话和案件图谱都保持稳定。
- 用户提出清晰完整的修改或新需求时，应执行到本地发布完成为止，让用户可以直接在页面上测试。
- 每个完整功能实现或运行时行为修改完成后，都要通过 `./scripts/publish-local.sh` 发布到本地，再交给用户手动测试。
- 发布流程可以通过 `./scripts/publish-local.sh` 自动完成校验、构建、静态资源同步、wheel 构建和安装。
- 测试策略要按风险判断：简单文档、文案、索引类修改不需要跑前端或 Python 测试；影响运行时、图谱状态、持久化、发布包或跨端契约的修改才需要有针对性验证。

## Brand Personality

品牌人格是「克制、可靠、专业、可追溯」。

界面应该像一个内部专家工作台：不抢戏，不堆装饰，状态表达明确，信息密度足够高。关系图区域要给用户稳定感，图上每个节点的位置、每条边的含义、每一步扩展的来源都应该清楚可依赖。

文案语气默认使用中文，短句、直接、可执行。技术名词可以保留英文，例如 WebSocket、PocketBase、runtime、wheel、case graph，但按钮、提示、工具提示和状态应优先中文化。面向业务动作时，优先使用用户熟悉的词：案件、上图分析、主体、账号、交易明细、上钻、下钻、双向钻取、排除、群组、线索。

## Anti-references

这个产品不应该像：

- 通用 AI 聊天壳：只有对话、会话列表和附件面板，不能承载案件研判的图谱主线。
- 营销型 AI 落地页：大标题、渐变英雄区、抽象口号不能替代真实工作流。
- 聊天玩具界面：过度拟人、过度动效、漂浮装饰会削弱专业性。
- 传统后台表单堆叠：所有能力塞进表格和弹窗会让图谱研判主线失焦。
- 一次性绘图工具：自动布局不能随意重排用户已经保存和分析过的图结构。
- 非标准 assistant-ui 拼装：为了保留旧实现而绕过 runtime、Composer、ThreadList 等官方抽象，会给后续迭代制造输入、会话和状态同步问题。
- 默认暴露所有小工具：复制、下载、全屏、删除等辅助动作应在 hover / focus 时出现，减少内容区噪声；触屏设备除外。

## Design Principles

1. **案件研判是主路径。** 当前案件、主体选择、关系图、钻取、交易明细和过程步骤优先级最高；聊天、文件和设置都服务这条主线。
2. **关系图是核心工作区。** 中间图形区域必须保持稳定、可读、可持续扩展。不要把图谱降级成普通图表或装饰性视图。
3. **布局位置必须被保护。** 图节点位置是用户研判过程的一部分。自动查询、扩图、钻取、刷新、加载和回放都不能移动已有节点；只能为新节点或缺失坐标的节点补位置。
4. **过程状态必须可追踪。** 每次关系分析操作都应该形成可恢复的状态，当前投影和步骤快照要能解释图是怎么一步一步形成的。
5. **业务语义优先于视觉炫技。** 上钻、下钻、双向钻取、交易核查、排除、群组、线索扩展等动作必须符合真实研判语义，不能只追求画面好看。
6. **G6 官方能力优先。** 开发图功能页面时，图渲染、布局、交互、插件、事件、拖拽、框选、右键菜单、缩放和视口能力优先使用 G6 官方方案；自定义代码主要负责业务数据适配和状态保护。
7. **标准抽象优先。** assistant-ui 已经提供的 runtime、primitive、adapter 和 thread list 能力，应优先作为对话实现基座；case-graph 的业务状态则应保持清晰的图谱领域模型。
8. **插件边界清晰。** WebUI-only 的 HTTP、WebSocket、sessions、uploads、settings、runtime compat 和 case-graph 逻辑留在插件内，不要求上游 nanobot core 为插件做特殊改动。
9. **清晰需求执行到可测状态。** 当修改或新需求已经清晰完整，就执行到本地发布完成，让用户可以直接在页面测试。
10. **验证要服务效率。** 不为简单修改机械跑测试；根据影响面选择最小有效验证。完整功能实现或运行时行为修改，仍需要发布到本地安装环境，再明确告知用户可以开始测试。

## Case-Graph Product Rules

上图分析是当前产品定位里的核心能力，相关改动必须遵守以下规则：

- 图谱结构不是临时渲染结果，而是案件研判过程资产。
- `graph.json` 表示当前关系图投影，`steps/*.json` 表示每次操作后的步骤快照，`facts/trades.jsonl` 表示当前图已纳入研判范围的交易事实。
- 交易级事实保存到 `facts/trades.jsonl`，`graph.json` 和步骤快照只保留 `factStore` 与 `edge.tradeIds` 引用，避免每一步重复写入完整流水；交易过滤应优先基于这些已沉淀事实重算图，而不是重新查库。
- `graph.layout.nodePositions`、节点 `x/y` 和旧版 `graphContent` 坐标都应该被视为已有布局证据。
- 扩图和钻取只能增量放置新节点，不允许重排旧节点。
- 图功能页面优先使用 G6 官方提供的布局、插件、行为和交互能力。
- 如果接入 G6 官方布局方案，必须采用已有节点固定、新节点增量布局的方式。
- 用户拖拽节点、未来手动重布局、未来重置布局等明确动作，才可以改变已有节点位置。
- 涉及布局的测试和验收必须覆盖“扩图后旧节点坐标不变”这一底线。

## Accessibility & Inclusion

默认目标是可达到 WCAG 2.1 AA 的产品可用性：键盘可达、焦点状态清晰、颜色不作为唯一状态表达、中文工具提示完整、触屏设备保留关键操作入口。

界面需要兼容浅色、深色和系统主题；减少非必要动效，动效只用于状态确认和空间变化。内容区 hover-only 工具必须同时支持 `:focus-within` 或 `:focus-visible`，移动和触屏环境不能因为没有 hover 而失去下载、复制或全屏能力。
