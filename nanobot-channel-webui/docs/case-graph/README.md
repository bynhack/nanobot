# Case Graph Docs

这组文档只记录当前 `nanobot-channel-webui` 上图产品事实、功能状态和待办问题。

当前不再以原版 `Ga-web + skyable-cloud` 作为实现目标或差异跟踪基线。原版项目中有不少实现问题，后续规划应以当前产品目标、用户工作流、过程文件和本项目代码为准。

当前上图分析已经是产品主路径之一。关系图不只是渲染结果，而是案件研判过程资产：
`graph.json` 保存当前投影，`steps/*.json` 保存每次关系分析后的步骤快照，
`graph.layout.nodePositions`、`positionMeta` 和 `groupLayout` 保存布局位置、来源、手动锁定和分组布局状态。已加载交易流水会沉淀到
`facts/trades.jsonl`，`graph.json` 和步骤快照只保留 `factStore` 与 `edge.tradeIds`
引用，把关系边和交易事实关联起来，避免交易事实随着步骤数重复膨胀。

当前应优先阅读：

- [feature-tracker.md](./feature-tracker.md)
  - 当前上图产品功能台账
  - 用于规划时快速区分 `Done / Partial / Missing / Deferred`
- [pending-fixes.md](./pending-fixes.md)
  - 当前产品仍待补齐的问题和决策点
  - 只记录本项目当前真实状态，不按原版差异建账

本地过程文件也必须作为布局和步骤事实来源：

- `~/.casework/workspace/data/case_graphs/**/graph.json`
- `~/.casework/workspace/data/case_graphs/**/steps/*.json`
- `~/.casework/workspace/data/case_graphs/**/facts/trades.jsonl`

## 图谱操作依据

图谱操作是案件研判过程的一部分。凡是删除、排除或人工写入案件研判事实的操作，
都必须在执行前记录操作依据；体现研判方向但可以快速恢复的操作允许选填依据；
查询、浏览和画布整理操作只自动留痕，不打断用户。

操作依据统一保存到步骤的 `operation.evidence`：

```json
{
  "level": "required",
  "reasonCode": "unrelated_to_case",
  "reasonLabel": "核实与本案无关",
  "note": "经询问确认属于正常经营关系"
}
```

- `required`：取消主体上图、排除交易流水、创建人工主体、补充人工资金往来、
  标注现实关系、补全关系，以及未来从历史步骤覆盖当前图。
- `optional`：恢复主体或交易、综合筛选后的主体调整、研判组创建/编辑/拆分/移出成员，
  以及修改钻取条件后的钻取。
- `automatic`：首次上图、普通钻取、筛选、布局、组收起/展开、缩放、平移、详情查看和
  历史只读预览，以及基于当前有效图谱生成的只读资金流向视图。

必填操作优先使用符合办案语义的快捷依据；只有选择“其他”时才强制输入补充说明。
创建交易主体、补充资金往来和标注现实关系直接复用各自表单已有的发现原因、来源材料、
情况说明、线索来源和关系说明，不重复展示通用依据控件；服务端会把这些业务字段整理为
步骤依据。
系统自动记录操作对象、执行时间、操作人和前后变化，用户不重复填写这些内容。
批量操作只填写一次依据，并关联整个步骤。AI 生成的图谱操作卡不得绕过同一规则。

旧步骤可以没有 `operation.evidence`，加载和回放时显示“未记录操作依据”，不反向伪造或
改写历史数据。依据一经写入步骤即作为过程记录只读展示，本期不提供修改和删除能力。

维护原则：

- 功能状态和规划视角写进 `feature-tracker.md`
- 当前待办、缺陷和开放决策写进 `pending-fixes.md`
- 不再新增或维护“原版实现对比 / 原版差异 / 原版问题”类跟踪文档
- 不再保留独立的过程计划文档作为当前事实来源
- 涉及扩图、钻取、补关系、恢复和回放的文档，必须写清楚已有节点坐标不可被全局自动重排；只有用户显式拖拽、未来明确的手动重布局/重置动作，或分组收起、展开、拆组这些明确整理动作，才能改变对应节点或组的位置
- 涉及图页面渲染、交互、插件、事件、拖拽、框选、右键菜单、缩放和视口能力时，优先使用 G6 官方方案；资金图首次上图优先使用 G6 同源布局算法做全局排布，后续增量扩图和分组整理使用自研增量布局引擎承载业务位置语义
