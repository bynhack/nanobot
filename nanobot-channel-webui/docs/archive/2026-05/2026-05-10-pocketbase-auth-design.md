# PocketBase 账号系统设计

## 目标

在 `nanobot-channel-webui` 插件内部新增一套轻量级账号系统，认证直接使用 `PocketBase` 内置 auth 能力，实现管理员与普通用户两类角色，并保证普通用户之间的会话、上传文件、运行数据完全隔离。

## 设计边界

- 只修改 [`/Users/brian/Documents/Project/nanobot/nanobot-channel-webui`](</Users/brian/Documents/Project/nanobot/nanobot-channel-webui>)
- 不修改 `nanobot/`、`webui/`、`bridge/` 等插件外代码
- `PocketBase` 由外部独立运行，插件只作为客户端接入
- 第一版不做公开注册，账号先通过 `PocketBase` 后台创建
- 第一版不迁移旧会话，只管理账号系统启用后的新会话

## 角色模型

认证直接使用 `PocketBase` 内置用户体系。

用户记录上增加一个扩展字段：

- `role = "admin" | "user"`

角色语义如下：

- `admin`
  - 可查看和管理所有用户进入新账号体系后的会话索引
  - 可查看所有用户上传文件与运行数据
  - 可使用完整设置页和运行观测页
- `user`
  - 仅可访问自己的会话
  - 仅可访问自己的上传文件
  - 仅可访问自己的运行数据
  - 默认最小权限，不可查看其他用户任何新数据

第一版不引入更复杂的角色表、组织模型或 ACL 体系。

## 数据模型

### 1. PocketBase 用户

直接使用 `PocketBase` auth collection。

关键字段：

- `email`
- `password`
- `role`

插件侧只消费：

- 用户 ID
- email
- role

### 2. PocketBase 会话索引 collection

新增一个插件专用 collection：`chat_sessions`

第一版建议字段：

- `owner`
  - relation -> users
- `chat_id`
  - string
- `session_key`
  - string
- `title`
  - string
- `preview`
  - string
- `last_activity_at`
  - datetime

职责：

- 作为“会话列表与权限索引层”
- 不保存完整消息正文
- 不替代本地 session 文件

### 3. 本地真实会话数据

真实消息历史继续保存在 nanobot 当前本地 session 文件体系中。

也就是说，系统会形成两层结构：

- `PocketBase chat_sessions`：负责权限边界和列表索引
- 本地 session 文件：负责真实消息历史

这样可以保持插件轻量，同时避免第一版就重做消息存储层。

## 会话列表策略

第一版中，会话列表的数据源以 `PocketBase chat_sessions` 为准。

含义是：

- 账号系统启用后，只展示已进入账号体系的新会话
- 旧本地会话不迁移，不进入新列表
- 普通用户查询自己的 `owner`
- 管理员查询全部索引

插件拿到索引记录后，再回查对应的本地 session 文件进行历史加载。

这样可以避免“旧会话扫描 + 新权限过滤”混合带来的复杂度。

## 认证流程

### 登录

前端新增登录入口，用户输入 `email + password`。

插件后端调用 `PocketBase` auth API：

- 成功：返回登录态，并建立插件当前用户上下文
- 失败：返回鉴权错误

插件不自行存储密码，不自造认证逻辑。

### 会话保持

插件需要保存当前登录态，并在每个请求进入时恢复当前用户上下文。

第一版只要求：

- 登录后维持会话
- 支持退出登录
- 未登录状态不能访问聊天主体与受保护设置页

第一版不要求：

- 找回密码
- 邮箱验证
- 第三方 OAuth

## 权限边界

### 1. 会话权限

- 普通用户只能查看自己 `owner` 的 `chat_sessions`
- 管理员可以查看全部 `chat_sessions`
- 加载历史时，必须校验当前用户是否有权访问该索引对应的 `chat_id`

### 2. 上传文件权限

上传目录从现在的按 `chat_id` 组织，扩展为按 `user_id/chat_id` 组织。

目标：

- 普通用户之间文件完全不可见
- 管理员可查看全部

第一版只要求对新上传文件使用新目录规则。

### 3. 运行数据权限

运行状态页面不再默认暴露全局数据给普通用户。

第一版策略：

- 管理员看到完整运行视图
- 普通用户只看到属于自己可见范围的运行信息

普通用户不需要拥有全局诊断能力。

## 主要模块拆分

### 1. PocketBase 集成层

新增一个轻量适配层，职责：

- 登录
- 读取当前用户
- 判断角色
- 读写 `chat_sessions`

不负责：

- 托管 `PocketBase`
- 直接存储完整聊天消息

### 2. 认证上下文层

负责在 HTTP / WebSocket 请求进入时建立当前用户上下文，并向内部服务暴露：

- 当前是否已登录
- 当前用户 ID
- 当前角色

### 3. 会话索引服务

负责：

- 新会话创建时写入 `PocketBase chat_sessions`
- 会话列表按角色过滤查询
- 删除会话时同步更新索引

### 4. 本地数据隔离服务

负责：

- 上传路径按 `user_id/chat_id` 隔离
- 运行数据按角色过滤

## UI 变化

第一版 UI 只做最小可用改动：

- 新增登录页或登录遮罩
- 未登录不可进入主聊天视图
- 管理员与普通用户共用登录入口
- 登录后根据角色展示不同范围的数据

第一版不追求复杂用户中心，不做注册页，不做资料编辑页。

## 错误处理

需要覆盖以下场景：

- `PocketBase` 不可达
- 登录失败
- token 失效
- 用户存在但缺少 `role`
- `chat_sessions` 索引存在，但本地 session 文件不存在

处理原则：

- 认证失败时给出明确错误
- 权限不足时拒绝访问
- 索引与本地文件不一致时，以“不可读取此会话”处理，并记录诊断信息

## 测试重点

第一版最关键的验证面：

- 登录成功 / 失败
- 管理员与普通用户角色分流
- 普通用户只能看到自己的新会话
- 普通用户不能加载其他用户会话
- 新上传文件落到 `user_id/chat_id` 隔离目录
- 管理员可见全局，普通用户不可见全局运行信息

## 分阶段策略

第一版只完成最小可用闭环：

1. `PocketBase` 登录
2. 角色判断
3. 新会话索引写入
4. 会话列表按用户过滤
5. 上传文件按用户隔离
6. 运行数据按角色收敛

以下内容明确留到后续：

- 公开注册
- 邀请码
- 用户资料页
- 旧会话迁移
- 完整消息正文入库

## 结论

这套方案的关键是：让 `PocketBase` 负责它最擅长的部分，也就是 auth 和轻量业务索引；让插件保留现有本地消息与文件体系，只在插件内部补上权限边界和会话索引映射。这样既符合轻量化目标，也能在第一版真正交付管理员 / 普通用户账号系统。*** End Patch
